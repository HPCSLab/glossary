# tidy-maps

map は用語を足すたびに末尾へ追記され、節の分類軸が崩れていく。このスキルは map を、新メンバーが**上から順に読んで分野を理解できる目次**へ戻す。判断は件数や文字列の一致ではなく、ノートの内容を読んだうえで行う。map の書式は `CLAUDE.md` の「map のテンプレート」に従う。

## 判断の観点

map を読むときに問うことである。いずれも内容を理解したうえでの判断であり、機械的な閾値は置かない。

- **節の分類軸**：各節について「この節の項目は何の一種か」を一語で言えるか。言えるなら、すべての項目がその問いに同じ種類の答えを返すか。例：「抽象化モデル」節にブロック・ファイル・オブジェクト・KVと並んで、B木やLSM木（データ構造）、RocksDBやGarnet（実装）が置かれていれば、軸が混ざっている。
- **読む順**：前提を読んでから後の節に進めるか。用語ノートの本文が前提として参照している用語が、map の上でも先に出ているか。
- **粒度**：節が大きすぎて読む順が見えなくなっていないか。小さすぎて独立した節である意味がないものはないか。
- **置き場所**：その用語を主題として扱うべき map はどれか。他の map の方が文脈として自然なら、そちらに移すか、参照として添えるに留める。同じ map の二つの節に同じ用語が載っていれば、どちらか一方に決める（「まず読む」での再掲は除く）。
- **一言説明**：用語ノートを読んだうえで、その説明が正確で、節の中で他の項目との違いが分かる書き方になっているか。
- **map の境界**：map 自体が二つの分野を抱えていないか。抱えていれば分割を提案する。

## 手順

### 1. すべて読む
引数の map（省略時は全 map）と `index.md` を読む。続いて、対象 map に載っている用語ノートと、`maps:` に対象 map を持つ用語ノートを**全文**読む。対象外の map も、移動先の候補として通読する。

完了条件：対象に関わる用語ノートをすべて全文読み終えている。一行定義だけで済ませたノートが残っていない。

### 2. 判断する
上の観点で map を見直し、理想の節立てを一から組む。現在の節立てを手直しするのではなく、用語の内容から「この分野を読む順」を先に決め、そこへ用語を配置する。全項目について、置く節（または移す map）と理由が言える状態にする。

あわせて、用語ノートの `maps:` が新しい配置と一致しているかを確かめる。

### 3. 再構成案を提示し、承認を得る
map ごとに次を示し、ユーザーの承認を待つ。承認前にファイルを編集しない。

- 新しい節立て（見出しと各節の項目名の骨子）と、その順にした理由
- 移動・他 map への移動・削除の一覧と、それぞれの理由（一行）
- `maps:` を直す用語ノートの一覧
- map の新設・分割の提案があればその案

### 4. 適用する
承認された案で map を書き換える。あわせて次を行う。

- 変更した map と用語ノートの `updated` を今日の日付にする（用語ノートは `maps:` を変えたものだけ）。
- 用語ノートの `maps:` を map の掲載と一致させる。
- map を新設・削除したら `index.md` の「分野」を更新する。
- 表の中の表示名付きリンクは `\|` でエスケープする。

### 5. 検証する
`git diff` を読み、元の map にあった項目が、意図して外したものを除いてすべてどこかの map に残っていることを確かめる。書き換えた map を上から通読し、読む順として自然に読めることを確かめる。

### 6. 報告とコミット
変更した map ごとに、節立ての変化と主な移動を短く報告する。作業ブランチ上なら map ごとに一つのコミットにまとめる。
